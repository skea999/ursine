# Go daemon migration — future design

**Status:** proposed, not implemented. Current release (0.7.0) is Rust.
**Scope:** daemon; GUI decision remains separate.

## Goal

A single static Go `ursined` binary that runs on Alpine/musl and glibc
distributions, while using the host's PAM stack. PAM is isolated in two Rust
helper binaries embedded in the Go daemon.

## Why the helper split

PAM is a C library that loads system PAM modules (`.so`) at runtime. A truly
static binary cannot load those modules. A dynamically linked daemon would
need a separate build per libc. The helper keeps the daemon static and limits
PAM memory-safety exposure to a short-lived child process.

## Architecture

```text
ursined (Go, CGO_ENABLED=0, static)
  ├─ embedded pam-helper-musl   (Rust, dynamic musl + system libpam)
  └─ embedded pam-helper-glibc  (Rust, dynamic glibc + system libpam)
```

Per authentication:

```text
ursined
  -> verify helper path/bytes
  -> select helper with --probe
  -> exec child with stdin/stdout pipes
  -> {user, password, service} JSON request
  -> {ok | unauthorized | expired | unavailable}
  -> timeout + process-group kill + bounded output
```

The daemon never calls `dlopen` or links PAM. The helper never accepts
credentials in argv or environment variables.

## Helper selection

Selection happens once at daemon startup and is fixed for the process
lifetime. Inputs never choose the helper.

1. Both helpers are embedded as bytes.
2. Each helper supports `--probe` and reports its libc and PAM availability.
3. The daemon tries the expected helper, then the other one.
4. If neither probe succeeds, authentication is `unavailable`; there is no
   stub fallback in production.

Pathless execution options:

- preferred: `memfd_create` + `/proc/self/fd/<n>` (no filesystem path);
- fallback: extract to `/run/ursine/` with root-only `0700` and execute there;
- never extract to a world-readable or user-writable directory.

The embedded bytes can still be extracted from a readable `ursined` binary.
That does not grant root because helpers are not setuid.

## Helper protocol

Use JSON lines over stdin/stdout, matching the daemon envelope style.

Request:

```json
{"user":"alice","password":"...","service":"ursine"}
```

Response:

```json
{"result":"ok"}
{"result":"unauthorized"}
{"result":"expired"}
{"result":"unavailable"}
```

Rules:

- password only on stdin, never argv/environment;
- clear or minimize the environment (`env_clear`);
- close unrelated file descriptors;
- bounded request/response sizes;
- fixed timeout;
- kill the process group on timeout;
- treat signals and nonzero exit as failure;
- no network, no shell, no user-controlled PAM service name.

## Build pipeline

Build helpers before the Go daemon:

```text
Alpine/musl container:
  cargo build --release -p ursine-pam-helper \
    --target x86_64-unknown-linux-musl
  # dynamic musl: -C target-feature=-crt-static

Debian baseline container (oldest supported glibc):
  cargo build --release -p ursine-pam-helper \
    --target x86_64-unknown-linux-gnu

Go build:
  CGO_ENABLED=0 go build -trimpath \
    -tags "netgo,osusergo" \
    -ldflags "-s -w -buildid=" \
    -o ursined ./cmd/ursined
```

The Go build embeds the two helper ELFs with `go:embed`. The daemon must be
built after the helpers and must record both hashes at build time.

Verification:

```bash
file ursined
ldd ursined                 # not a dynamic executable
readelf -d ursined          # no NEEDED entries
file pam-helper-musl
file pam-helper-glibc
```

## Packaging

One tarball can contain:

```text
bin/ursined
bin/ursine                 # GUI, still platform-specific
share/...                  # PAM service, units
```

Helpers are inside `ursined`; no public helper files are required.

Limits:

- the glibc helper must be built against the oldest supported glibc;
- the musl helper must be built against the target musl baseline;
- PAM modules and `/etc/pam.d/ursine` remain system files;
- NixOS may not resolve a Debian-built helper's `libpam.so.0`; it may need a
  Nix-built helper or a controlled PAM library search path.

## Nix

The Go daemon can be built with `buildGoModule` and `CGO_ENABLED=0`.
The helper is a separate derivation linked to the Nix PAM package.

Do not assume the Debian-built glibc helper works on NixOS. Test:

- `libpam.so.0` resolution;
- PAM module directory;
- `/etc/pam.d/ursine` generated by the NixOS module;
- helper probe and real authentication.

If the embedded Debian helper cannot resolve Nix paths, Nix must build and
install its own helper variant. In that case the Nix package is not the same
artifact as the universal tarball.

## GUI

A static Go daemon does not make the GUI portable.

- Rust/libcosmic GUI: dynamic musl today; separate glibc build needed for
  glibc hosts; a single static GUI is not realistic because wgpu/Vulkan/EGL
  load system libraries.
- Go native GUI: no mature toolkit meets native, static, memory-safe and
  system-theme requirements. Fyne/Gio use cgo; go-gui uses runtime EGL/X11;
  Wain and go-widgets are experimental.
- Web UI: Go server is static and memory-safe, but the frontend is web.

Therefore:

- daemon-only portability: achievable with this design;
- whole-product single artifact: not achievable with the current native GUI.

## Security boundary

- Go daemon: memory-safe, static, no PAM linkage.
- Rust helper: our code is memory-safe; PAM and its modules are C.
- Helper runs as root because PAM must read system account data.
- Process isolation protects the daemon heap, not the host: a compromised
  root helper can still compromise the system.
- Never install helpers setuid.
- Root-only helper extraction (`0700`) prevents unprivileged execution.
- Rate-limit authentication and bound helper concurrency to contain crashes
  and fork/exec abuse.
- Embedded helpers are coupled to daemon releases; a helper fix requires a
  daemon release.

## CI tests

Required matrix:

1. Alpine/musl: static daemon, musl helper probe, PAM success/failure/expired.
2. Debian/glibc: static daemon, glibc helper probe, PAM success/failure.
3. NixOS: helper PAM path and module resolution.
4. Wrong-helper probe fails closed.
5. Helper crash/timeout returns auth failure and daemon stays alive.
6. Password absent from argv, environment, logs and audit.
7. `ldd`/`readelf` assert the daemon is static.
8. Packaging checks helper hashes and root-only extraction permissions.

## Migration phases

1. Extract PAM into a Rust helper crate with JSON-lines protocol and tests.
2. Add embedded-helper execution and runtime selection to the current daemon.
3. Switch the daemon build to static musl; remove direct PAM linkage.
4. Add glibc helper build job and baseline tests.
5. Add Nix helper path tests.
6. Only then consider porting the daemon to Go; the helper protocol is
   language-neutral.
7. GUI migration is a separate decision; do not couple it to the daemon.

## Open questions

- NixOS PAM library/module resolution for an embedded glibc helper.
- Oldest glibc baseline to support.
- memfd execution support on all target kernels; fallback policy.
- Whether the release package ships one universal tarball or per-libc GUI
  variants.
- Helper update policy and emergency release process.
